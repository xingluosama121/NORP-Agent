## 第 1 章 快速开始：5 分钟写出第一个插件

### 1.1 找到插件目录

插件放在「插件目录」里。有两种方式查看/设置插件目录：

- **方式 A（推荐）**：打开 NORP Agent →「插件控制面板」→ 点「添加插件目录」，选择或新建一个文件夹（例如 `D:\my_plugins`）。
- **方式 B（手动）**：编辑 `%LOCALAPPDATA%\vibe_agent\config.json`，把目录路径加入 `plugin_dirs` 列表：

```json
{
  "plugin_dirs": ["D:/my_plugins"]
}
```

项目自带的 `plugins/` 与 `official_plugins/` 目录就是现成的插件目录，也可以直接往里面放文件。

### 1.2 写你的第一个插件

在插件目录里新建一个文件，名字随意（不要叫 `__init__.py`），例如 `my_first_plugin.py`，内容如下：

```python
PLUGIN_NAME = "My First Plugin"
PLUGIN_PUBLISHER = "你的名字"
PLUGIN_VERSION = "1.0.0"
PLUGIN_DESCRIPTION = "我的第一个插件：提供一个问候工具"

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "say_hello",
            "description": "向用户问好，返回一条问候语。",
            "parameters": {
                "type": "object",
                "properties": {
                    "name": {
                        "type": "string",
                        "description": "要问候的名字"
                    }
                },
                "required": [],
                "additionalProperties": False
            }
        }
    }
]


def execute(tool_name: str, args: dict, context) -> str:
    """Agent 调用本插件的工具时，会进入这个函数。"""
    if tool_name == "say_hello":
        name = args.get("name", "世界")
        return f"你好，{name}！—— 来自 My First Plugin"
    return f"未知工具: {tool_name}"
```

就这些。**三部分：元数据常量、TOOLS 列表、execute 函数。**

### 1.3 让 NORP 加载它

- 在插件控制面板点「重新加载插件」，或重启 NORP Agent。
- 如果一切正常，插件控制面板里会出现「My First Plugin」，状态为启用，工具数为 1。

### 1.4 让 Agent 使用它

在主界面输入：

```
用 say_hello 工具向张三问好
```

Agent 会自己发现并调用 `say_hello` 工具，返回「你好，张三！—— 来自 My First Plugin」。

> 默认配置下，插件工具调用需要你在弹窗里点「批准」（人工审批），这是安全设计，见 [第 7 章](#第-7-章-安全模型必读)。

### 1.5 注意：默认安全配置可能拦截你的插件

NORP 的默认安全配置是「最严格」的（见第 7 章）：

| 配置 | 默认值 | 对你的影响 |
|---|---|---|
| `plugin_security_audit` | `block` | 代码里有危险调用（如 `subprocess`）会被**拒绝加载** |
| `plugin_security_import_restrict` | `strict` | 只允许导入白名单模块（json / os.path / re 等），`import requests` 会失败 |
| `plugin_security_require_permissions` | `true` | 需要 manifest.json 声明权限（单文件插件无 manifest 时按无权限处理） |
| `plugin_network_policy` | `deny` | 插件不能访问网络 |

上面第 1.2 节的示例只用到了 `json` / 基础语法，完全在安全范围内，可以正常加载。

如果你想让插件做「危险」的事（执行命令、访问网络），请阅读 [第 7 章](#第-7-章-安全模型必读)，了解如何安全地声明权限、签名、放宽策略。**不要为了省事直接关闭全部安全开关。**

## 第 2 章 插件的基本结构

### 2.1 两种布局

插件可以是**单个 .py 文件**，也可以是一个**文件夹（包插件）**：

```
plugins/
├── my_tool.py              # 布局 A：单文件插件（最常见、最简单）
└── fancy/                  # 布局 B：包插件（需要 manifest.json）
    ├── manifest.json       #   插件元数据 + 权限声明 + 签名
    └── plugin.py           #   入口文件（entry，默认名 plugin.py）
```

- 单文件插件：**入口文件本身**就是 `xxx.py`，元数据写在文件顶部的 `PLUGIN_*` 常量里。
- 包插件：目录下必须有 `manifest.json`，`manifest.json` 里指定入口文件（默认 `plugin.py`），元数据也可以写在 manifest 里（`name` / `version` / `publisher` / `description`），入口文件里的 `PLUGIN_*` 常量作为补充。

### 2.2 插件的四要素

| 要素 | 必填 | 说明 |
|---|---|---|
| `PLUGIN_NAME` | 是 | 插件显示名（全局唯一，重名会覆盖） |
| `TOOLS` | 否 | 工具定义列表（OpenAI function schema），没有则为 `[]` |
| `execute()` | 否 | 工具执行函数；有 TOOLS 时必须提供 |
| 钩子函数 | 否 | 15 个可选钩子，见第 4 章 |

> 如果插件**既没有 TOOLS、也没有钩子、也没有 execute()**，会被判定为「不是插件」而跳过加载（也不会报错）。

### 2.3 元数据常量（写在文件顶部）

```python
PLUGIN_NAME = "插件显示名"          # 必填，全局唯一
PLUGIN_PUBLISHER = "作者"           # 可选，默认 ""
PLUGIN_VERSION = "1.2.0"            # 可选，默认 "0.0.0"
PLUGIN_DESCRIPTION = "一句话介绍"    # 可选，默认 ""
```

**加载流程（了解即可）**：插件文件被扫描到后，NORP 依次执行：

1. **签名校验**（若开启）：验 Ed25519 签名，`INVALID`（签名损坏/文件被改）→ 直接拒绝加载。
2. **安全审计**（AST 静态扫描源码）：发现 `CRITICAL` 级危险模式且审计级别为 `block` → 拒绝加载。
3. **权限检查**（若开启 `require_permissions`）：manifest 声明的权限必须覆盖审计发现的危险操作。
4. **加载**：默认在**独立子进程**（plugin_host）中 `import` 插件模块（进程隔离）。
5. **注册**：通过全部检查后，才把 TOOLS 与钩子注册进 PluginManager。

第 7 章会详细讲每一步。

## 第 3 章 注册工具：让 Agent 调用你的能力

### 3.1 TOOLS 是什么

`TOOLS` 是一个列表，每个元素是一个 **OpenAI function schema**（与 OpenAI API 的 `tools` 参数格式完全一致）。Agent（LLM）看到这些定义后，会决定「什么时候调用、传什么参数」。

### 3.2 一个工具定义的完整结构

```python
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "weather_query",                        # 工具名（全局唯一）
            "description": "查询指定城市的天气。返回温度、天气状况、风力。",  # 描述越详细，Agent 用得越准
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名，如 北京 / Shanghai"
                    },
                    "days": {
                        "type": "integer",
                        "description": "预报天数，1~7",
                        "default": 3
                    }
                },
                "required": ["city"],                       # 必填参数
                "additionalProperties": False
            }
        }
    },
    # 可以再定义第二个工具……
]
```

### 3.3 编写优秀工具描述的 5 条建议

1. **description 写清楚「做什么 + 返回什么」**：`"查询笔记并按时间倒序返回列表"` 好于 `"查询笔记"`。
2. **参数 description 给出示例值**：`"城市名，如 北京 / Shanghai"`。
3. **必填参数放进 `required`**，可选参数给出 `default`。
4. **`additionalProperties: False`**：约束 LLM 不要传多余字段。
5. **工具名用动词 + 名词**（`save_note` / `list_notes` / `search_notes`），不要用中文名。

### 3.4 execute()：工具的执行入口

```python
def execute(tool_name: str, args: dict, context) -> str:
    ...
```

- `tool_name`：被调用的工具名（你的插件可以注册多个工具，在这里分发）。
- `args`：LLM 传过来的参数（dict）。
- `context`：PluginContext 对象（见第 5 章）。
- **返回值必须是字符串**（或可转成字符串的对象），这是 Agent 观察到的工具结果。返回的字符串会进入 LLM 上下文，所以请返回**结构化、简洁**的文本（可以用 Markdown）。

示例：多工具分发

```python
def execute(tool_name: str, args: dict, context) -> str:
    if tool_name == "weather_query":
        return _handle_weather(args, context)
    if tool_name == "weather_history":
        return _handle_history(args, context)
    return f"未知工具: {tool_name}"
```

### 3.5 工具调用时的确认

默认配置（`approval_enabled: true`）下，**所有插件工具的调用都需要你在弹窗里人工批准**。这是安全设计——插件工具名由插件自定义，无法像原生工具那样预映射风险级别，因此总开关开启时一律全审。你可以在插件控制面板关闭「插件工具调用审批」（不推荐）。

### 3.6 关于名字冲突

- **工具名全局唯一**：两个插件注册同名工具时，先注册的生效，后注册的被跳过并打警告日志。
- **插件名全局唯一**：同名插件（入口文件不同但 `PLUGIN_NAME` 相同）后加载的覆盖先加载的（旧工具/钩子先被卸载）。

## 第 4 章 钩子（Hooks）：订阅 Agent 的生命周期

钩子让你在 Agent 的**特定时刻**执行自己的代码。NORP 共定义 **15 个钩子，分 4 层**。

> 钩子签名中，**最后一个参数永远是 `context`**（PluginContext）。钩子内部出错会被静默吞掉（`except Exception: pass`），**绝不影响 Agent 主流程**——这是硬性保证，你可以放心写钩子。

### 4.1 钩子总览

| 层 | 钩子 | 触发时机 | 签名 | 可变 |
|---|---|---|---|---|
| L1 生命周期 | `on_agent_init` | Agent 启动完成 | `(context)` | 否 |
| L1 生命周期 | `on_agent_shutdown` | Agent 关闭 | `(context)` | 否 |
| L2 任务 | `on_task_start` | 新任务开始 | `(task_text, context)` | 否 |
| L2 任务 | `on_task_done` | 任务正常完成 | `(summary, final_reply, context)` | 否 |
| L2 任务 | `on_task_error` | 任务出错 | `(error_msg, context)` | 否 |
| L2 任务 | `on_task_stopped` | 任务被用户停止 | `(context)` | 否 |
| L2 任务 | `on_task_timeout` | 任务超时 | `(elapsed, context)` | 否 |
| L3 步骤 | `before_step` | 每步 ReAct 开始 | `(step, messages, context)` | **是** |
| L3 步骤 | `after_step` | 每步 ReAct 结束 | `(step, reasoning, content, tool_calls, context)` | 否 |
| L3 步骤 | `before_tool_call` | 每次工具调用前 | `(tool_name, args, context)` | **是** |
| L3 步骤 | `after_tool_call` | 每次工具调用后 | `(tool_name, args, result, context)` | **是** |
| L3 步骤 | `on_user_input_required` | Agent 需要用户输入 | `(question, context)` | 否 |
| L4 流式 | `on_reasoning` | 输出思考 token | `(token, context)` | 否 |
| L4 流式 | `on_content` | 输出正文 token | `(token, context)` | 否 |
| L4 流式 | `on_event` | 事件队列事件 | `(event_type, data, context)` | 否 |
| L4 流式 | `on_usage_update` | token 用量更新 | `(usage, context)` | 否 |

### 4.2 三个「可变钩子」（重要）

`before_step` / `before_tool_call` / `after_tool_call` 的返回值可以**修改数据流**：

| 钩子 | 返回 | 效果 |
|---|---|---|
| `before_step` | 返回 `messages` 列表（可修改后返回） | 修改进入该步的对话消息；返回非 list 则忽略 |
| `before_tool_call` | 返回 `dict` | 用返回值**替换**工具参数（改写参数）；返回 `None` 表示不修改、放行 |
| `after_tool_call` | 返回 `str` | 用返回值**替换**工具结果；返回 `None` 表示不修改 |

规则：多个插件监听同一钩子时，**第一个返回非 `None` 的监听者的返回值生效**（先到先得）。

```python
def before_tool_call(tool_name: str, args: dict, context):
    """示例：给所有 write_file 调用自动加时间戳后缀（改写参数）。"""
    if tool_name == "write_file":
        args = dict(args)
        args["path"] = args["path"] + ".bak"
        return args          # 返回 dict = 替换参数
    return None              # 返回 None = 不修改，放行


def after_tool_call(tool_name: str, args: dict, result: str, context):
    """示例：把错误结果替换成友好提示（改写结果）。"""
    if "Error" in result:
        return f"工具执行失败，请重试。原始信息：{result[:100]}"
    return result
```

> 注意：`before_tool_call` 返回 `None` 表示「放行不修改」（多个监听者全部返回 None 也放行）。它**不能**单独阻断调用——想拦截，请用「钩子里不返回值 + 抛出异常」的方式？也不行，异常会被吞。若你需要阻断能力，请通过安全层（审批/网络策略/审计）实现，或联系主程序扩展。

### 4.3 钩子超时与僵尸线程

- 每个钩子回调的**硬超时是 5 秒**（`HOOK_TIMEOUT = 5.0`）。
- 超时的钩子线程会被标记为「僵尸线程」，在 Agent 关闭时统一回收。
- 因此：**钩子内不要做耗时操作**（网络请求、大文件读写、`time.sleep`）。需要耗时逻辑时，用后台线程：

```python
import threading

def on_task_done(summary: str, final_reply: str, context):
    def _slow_work():
        # 耗时逻辑：写文件、发请求……
        pass
    threading.Thread(target=_slow_work, daemon=True).start()
```

### 4.4 流式钩子的性能警告

`on_reasoning` / `on_content` 是**每输出一个 token 触发一次**的，非常高频。在这两个钩子里：

- 禁止做磁盘 IO、网络 IO、打印大段内容。
- 建议只做轻量计数或直接 `pass`（参考官方插件 example_notifier 的做法）。

## 第 5 章 上下文对象 PluginContext 完整参考

每个插件的每个钩子/工具调用都会收到一个 `PluginContext` 对象（按插件名独立实例）。

```python
context.project_root   # str：当前工作区绝对路径
context.app_dir        # str：应用数据目录（config/memories/logs，日志也写在这里）
context.config         # dict：config.json 的只读快照（每次调用自动刷新）
context.storage        # dict：插件私有 KV 存储，跨钩子存活于整个 Agent 会话
context.logger         # SimpleLogger：插件专属日志器
context.current_step   # int：当前 ReAct 步数
context.total_usage    # dict：累计 token 用量 {"input_tokens":.., "output_tokens":.., "tool_call_tokens":..}
```

### 5.1 storage：跨钩子共享状态

`storage` 是普通 dict，**在一次 Agent 会话内**跨钩子、跨工具调用存活：

```python
def on_agent_init(context):
    context.storage["start_time"] = time.time()
    context.storage["tool_call_count"] = 0

def after_tool_call(tool_name, args, result, context):
    context.storage["tool_call_count"] = context.storage.get("tool_call_count", 0) + 1

def on_agent_shutdown(context):
    elapsed = time.time() - context.storage.get("start_time", time.time())
    context.logger.info(f"本会话共调用工具 {context.storage.get('tool_call_count', 0)} 次，时长 {elapsed:.0f}s")
```

### 5.2 logger：插件专属日志

```python
context.logger.info("普通信息")
context.logger.warn("警告")
context.logger.error("错误")
context.logger.debug("调试信息")
```

- 日志同时输出到控制台与 `<app_dir>/plugin.log`（所有插件共用一个文件，每行带插件名）。
- 日志行格式：`[时间] [级别] [插件名] 消息`。

### 5.3 config：只读配置快照

`context.config` 是 config.json 的**只读快照**（每次调用自动刷新）。你可以读取任何配置项，例如：

```python
model = context.config.get("model", "")
vision_enabled = context.config.get("vision_enabled", False)
```

> 不能修改 config（它是副本）。想改配置请通过前端设置面板。

## 第 6 章 完整示例：从零写一个「任务统计」插件

综合运用工具 + 钩子 + storage + logger，写一个「任务统计」插件：

- 工具：`get_session_stats` —— 查询本次会话的统计信息。
- 钩子：记录会话开始时间、统计每步/工具调用次数、任务完成时自动写一份统计文件。

```python
PLUGIN_NAME = "Session Stats"
PLUGIN_PUBLISHER = "Your Name"
PLUGIN_VERSION = "1.0.0"
PLUGIN_DESCRIPTION = "统计本次 Agent 会话的步数、工具调用与耗时。"

import json
import os
import threading
import time

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_session_stats",
            "description": "返回本次 Agent 会话的统计信息：已执行步数、工具调用次数、会话时长（秒）。",
            "parameters": {
                "type": "object",
                "properties": {},
                "required": [],
                "additionalProperties": False
            }
        }
    }
]


def execute(tool_name: str, args: dict, context) -> str:
    if tool_name == "get_session_stats":
        elapsed = time.time() - context.storage.get("start_time", time.time())
        return (
            f"**会话统计**\n"
            f"- 已执行步骤: {context.storage.get('steps', 0)}\n"
            f"- 工具调用次数: {context.storage.get('tool_calls', 0)}\n"
            f"- 会话时长: {elapsed:.0f} 秒"
        )
    return f"未知工具: {tool_name}"


# ── 钩子 ──────────────────────────────────────────────────

def on_agent_init(context):
    context.storage["start_time"] = time.time()
    context.storage["steps"] = 0
    context.storage["tool_calls"] = 0
    context.logger.info("Session Stats 已启动")


def before_step(step: int, messages: list, context):
    context.storage["steps"] = step
    return messages  # 不修改消息，原样返回


def before_tool_call(tool_name: str, args: dict, context):
    context.storage["tool_calls"] = context.storage.get("tool_calls", 0) + 1
    return None  # 不修改参数


def on_task_done(summary: str, final_reply: str, context):
    """任务完成时把统计写进文件（用后台线程，避免阻塞钩子链）。"""
    def _save():
        try:
            stats = {
                "summary": summary[:100],
                "steps": context.storage.get("steps", 0),
                "tool_calls": context.storage.get("tool_calls", 0),
                "elapsed_sec": round(time.time() - context.storage.get("start_time", time.time()), 1),
            }
            path = os.path.join(context.app_dir, "session_stats.json")
            with open(path, "w", encoding="utf-8") as f:
                json.dump(stats, f, ensure_ascii=False, indent=2)
            context.logger.info(f"统计已写入 {path}")
        except Exception:
            pass

    threading.Thread(target=_save, daemon=True).start()


def on_agent_shutdown(context):
    elapsed = time.time() - context.storage.get("start_time", time.time())
    context.logger.info(
        f"会话结束：{context.storage.get('steps', 0)} 步，"
        f"{context.storage.get('tool_calls', 0)} 次工具调用，耗时 {elapsed:.0f}s"
    )

## 第 7 章 安全模型（必读！）

NORP 对插件有一套**多层纵深防御**。默认配置是「最严格」的：宁可拒绝，不可放行。理解它，你才能写出「既强大又不会被拦」的插件。

### 7.1 安全层级总览

```
插件文件
   │ ① 签名校验（plugin_signature_verify，默认开）
   │    INVALID → 拒绝加载；TRUSTED → 放宽审计；UNTRUSTED/UNSIGNED → 按用户配置
   ▼
   │ ② AST 静态审计（plugin_security_audit，默认 block）
   │    扫描源码中的危险调用模式，CRITICAL 级且 block → 拒绝加载
   ▼
   │ ③ 权限声明检查（plugin_security_require_permissions，默认开）
   │    manifest.permissions 必须覆盖审计发现的危险操作
   ▼
   │ ④ 加载执行（plugin_isolation，默认 process）
   │    独立子进程加载，插件崩溃不影响主进程
   ▼
   │ ⑤ 运行时：导入限制（plugin_security_import_restrict，默认 strict）
   │    插件 import 危险模块 → ImportError
   │ ⑥ 运行时：网络策略（plugin_network_policy，默认 deny）+ SSRF 防护
   │ ⑦ 运行时：人工审批（approval_enabled，默认开）
   │    插件工具调用需人工确认
   ▼
   Agent 使用插件工具
```

### 7.2 审计级别：`plugin_security_audit`

| 值 | 行为 |
|---|---|
| `off` | 不审计，全部放行（不推荐） |
| `warn` | 只警告，不拦截 |
| `block`（默认） | 发现 **CRITICAL** 级危险模式 → 拒绝加载 |

**CRITICAL 级模式**（出现即可能被拒）：`os.system` / `os.popen` / `subprocess.*` / `eval` / `exec` / `compile` / `__import__` / `importlib.import_module` / `ctypes` / `cffi` / `os._exit` / `os.kill`，以及**动态绕过**（`getattr(os, "system")`、`os.__dict__["system"]`、`globals()["os"]` 等反射访问）。

**WARNING 级模式**（block 时不拦截，但会记录；`require_permissions` 开启时可能要求声明权限）：`os.remove` / `shutil.rmtree` / `os.chmod` / `socket` / `http` / `urllib` / `requests` / `ftplib` / `smtplib` / `pickle` / `marshal` / `yaml.unsafe_load` / `sys.modules` 修改 / `sys.settrace` / `builtins` 修改 / `sys.exit` 等。

> 信任分级：**签名有效且公钥受信任**（TRUSTED）的插件，审计自动放宽为 `warn`、导入限制自动降为 `off` —— 这是官方插件和可信发布者的通道。见 7.6。

### 7.3 导入限制：`plugin_security_import_restrict`

| 值 | 行为 |
|---|---|
| `off` | 不限制导入（受信任插件默认此档） |
| `safe` | 禁止导入危险模块：subprocess / ctypes / cffi / socket / pickle / marshal / telnetlib / ftplib / smtplib |
| `strict`（默认） | **只允许**白名单模块（见下），其余全部拒绝 |

`strict` 白名单（STRICT_SAFE_MODULES）：`json re datetime math random collections itertools functools typing enum pathlib os.path textwrap string hashlib base64 traceback logging warnings copy uuid time plugin_system.context`。

`safe` 档额外放行：`os` / `shutil` / `io` / `tempfile` / `csv` / `html` / `xml` / `struct` / `codecs` / `decimal` / `statistics` / `glob` / `fnmatch` / `inspect` / `contextlib` / `pprint` / `calendar` / `zoneinfo` / `fractions` / `unicodedata` / `xml.etree.ElementTree`。

> 注意：`strict` 下 `import requests`、`import subprocess` 都会抛 `ImportError`，插件加载/执行时直接失败。需要网络或进程能力的插件，请走「签名 + 信任」路线（官方/可信发布者），或与管理员协商放宽策略。

### 7.4 权限声明：`plugin_security_require_permissions`

默认开启。要求包插件的 `manifest.json` 中 `permissions` 字段覆盖审计发现的危险操作：

| 审计发现的类别 | 需要声明的权限 |
|---|---|
| `shell_exec` / `code_exec` / `native_exec` / `process_terminate` | `"process"` |
| `network` | `"network"` |
| `file_delete` / `file_move` | `"file_write"` |
| `dangerous_import`（subprocess / socket） | `"process"` / `"network"` |

```json
{
  "name": "My Plugin",
  "permissions": ["network", "file_write"]
}
```

权限不足 → 拒绝加载，错误信息会提示缺失的权限。单文件插件没有 manifest，视为未声明权限（`require_permissions` 开启时，带危险操作的**单文件插件会被拒**——这是设计使然，安全优先；请改用包插件 + 签名）。

### 7.5 进程隔离：`plugin_isolation`

| 值 | 行为 |
|---|---|
| `process`（默认） | 插件在**独立子进程**（`plugin_system.plugin_host`）中加载执行，主进程通过 JSON 行协议 RPC 调用。插件崩溃/死循环/内存泄漏只影响子进程，主进程可 kill 重启 |
| `inprocess` | 插件直接挂载到主进程（仅限开发调试，不推荐，安全收益为零） |

进程隔离模式下：

- 插件模块对象只存在于子进程，**无法直接访问/修改主进程**。
- 插件 `print` 输出不会进入主进程 stdout（被子进程捕获）。
- 插件上下文通过 RPC 同步（`project_root` / `app_dir` / `config` / `current_step` / `total_usage`；`storage` 保留在子进程内，跨调用持久）。
- `execute()` 返回非字符串对象时，会自动转成 JSON 可序列化形式（否则转字符串）。

### 7.6 签名校验：`plugin_signature_verify`（Ed25519）

NORP 插件签名协议 v1：

- 算法：**Ed25519**（cryptography 库）。
- 签名对象：插件入口文件字节的 **SHA-256 摘要**（与文件编码无关，跨平台稳定）。
- 存储：包插件 → `manifest.json` 的 `"signature"` 字段；单文件插件 → sidecar 文件 `<入口文件>.sig`（JSON）。
- 信任模型：内置 NORP Studio 官方公钥 + `plugin_trusted_keys` 追加的用户信任公钥。

校验结果四种状态：

| 状态 | 含义 | 处置 |
|---|---|---|
| `trusted` | 验签通过 + 公钥受信任 | **审计放宽为 warn、导入限制 off**（信任通道） |
| `untrusted` | 验签通过但公钥不在信任列表 | 按用户配置审计/限制 |
| `unsigned` | 无签名信息 | 按用户配置审计/限制 |
| `invalid` | 验签失败（文件被篡改/签名损坏） | **拒绝加载** |

签名工具用法（见 [第 9 章](#第-9-章-插件签名与分发)）：

```bash
python _sign_plugin.py gen                              # 生成密钥对
python _sign_plugin.py sign my_plugin.py --key <私钥>    # 签名（生成 my_plugin.py.sig）
python _sign_plugin.py verify my_plugin.py --key <公钥>  # 验签
python _sign_plugin.py sign-dir plugins/ --key <私钥>    # 批量签名
```

### 7.7 网络策略：`plugin_network_policy`（四粒度 + SSRF 防护）

| 值 | 行为 |
|---|---|
| `deny`（默认） | 插件禁止访问任何网络 |
| `audited_public` | 仅允许命中白名单的公网 URL/域名（`plugin_network_url_allowlist` / `plugin_network_domain_allowlist`，支持前缀匹配） |
| `public_only` | 允许全部公网，禁止内网/环回/链路本地 |
| `allow_all` | 允许全部（含内网；仅建议受信任插件） |

**SSRF 防护（硬约束）**：只要策略不是 `allow_all`，一律拦截：私网网段、环回、链路本地、保留网段、组播、以及云元数据地址（`169.254.169.254`、`metadata.google.internal` 等）；`localhost`、`.local`、`.internal`、`.lan` 域名也判为内网。DNS 解析后的每个 IP 都会检查（防 DNS rebinding）。

> 实现说明：`NetworkPolicy.check_url()` 是纯裁决引擎（无副作用），配置与查询 API 已就绪（`get_plugin_security_config` / `set_plugin_security_config`），当前版本插件代码内的实际网络调用尚未自动接入该网关（计划接入中）。因此：**插件内请自觉遵守策略**（先 `check_url` 再发请求）；主程序后续版本会把它接入统一出口。

### 7.8 人工审批：`approval_enabled`

- 开启（默认）后，**所有插件工具调用**都会弹窗请求用户批准。
- 与原生工具确认（`native_confirm_*`，管 write_file / delete_file / exec_cmd）是两套独立策略，互不影响。
- 前端弹窗会标注「插件工具」标识。

### 7.9 安全配置对照表（config.json）

```json
{
  "plugins_enabled": true,
  "plugin_dirs": [],
  "plugin_security_audit": "block",
  "plugin_security_import_restrict": "strict",
  "plugin_security_require_permissions": true,
  "plugin_security_resource_limit": false,
  "plugin_isolation": "process",
  "plugin_signature_verify": true,
  "plugin_trusted_keys": [],
  "plugin_network_policy": "deny",
  "plugin_network_url_allowlist": [],
  "plugin_network_domain_allowlist": [],
  "approval_enabled": true,
  "native_confirm_enabled": true,
  "native_confirm_write": true,
  "native_confirm_delete": true,
  "native_confirm_exec": true
}
```

### 7.10 想写「能干重活」的插件？推荐路径

```
1. 用包插件布局（manifest.json）
2. 在 manifest 里声明 permissions（network / process / file_write）
3. 用 _sign_plugin.py 生成密钥对并签名
4. 把公钥加入 config.json → plugin_trusted_keys（或交给官方签名）
5. 加载后即为 trusted：审计放宽、导入不限、网络策略可单独配置
```

**绝对不要**为了省事把所有安全开关关掉——那等于把主进程和你的电脑暴露给任意插件。

## 第 8 章 包插件与 manifest.json

当插件需要「权限声明 / 签名 / 多个文件」时，用包插件布局：

```
fancy/
├── manifest.json
└── plugin.py          # 入口文件（默认名 plugin.py，可配置）
```

### 8.1 manifest.json 字段

```json
{
  "name": "Fancy Plugin",
  "version": "1.0.0",
  "publisher": "Your Name",
  "description": "一个包插件示例",
  "entry": "plugin.py",
  "enabled": true,
  "permissions": ["network", "file_write"],
  "signature": {
    "algorithm": "ed25519",
    "public_key": "<公钥 hex>",
    "signature": "<签名 hex>",
    "signed_files": ["plugin.py"]
  }
}
```

| 字段 | 说明 |
|---|---|
| `name` | 插件名（若入口文件也定义了 `PLUGIN_NAME`，以入口文件的为准） |
| `version` / `publisher` / `description` | 元数据（入口文件的 `PLUGIN_*` 常量优先级更高） |
| `entry` | 入口文件相对路径，默认 `plugin.py` |
| `enabled` | `false` 则跳过加载 |
| `permissions` | 权限声明（见 7.4），`require_permissions` 开启时校验 |
| `signature` | 签名块（见第 9 章），`signed_files` 列出签名覆盖的文件 |

### 8.2 manifest 与 PLUGIN_* 常量的优先级

- 插件名：**入口文件的 `PLUGIN_NAME` 优先**（manifest 的 `name` 作为后备）。
- version / publisher / description：**入口文件常量优先**（manifest 值作为后备）。
- enabled：manifest 的 `enabled` 决定是否加载。

## 第 9 章 插件签名与分发

签名让用户信任你的插件（加载后进入 trusted 通道：审计放宽、导入不限）。

### 9.1 准备

```bash
pip install cryptography
```

### 9.2 生成密钥对（私钥务必保密！）

```bash
python _sign_plugin.py gen
```

输出：

```
PUBLIC_KEY = <64 位 hex>
PRIVATE_KEY = <64 位 hex>
```

- **公钥**：发布给用户，用户把它加入 `config.json → plugin_trusted_keys`（或你申请加入官方公钥）。
- **私钥**：留在自己本地，**绝不提交到代码库**。

### 9.3 签名单文件插件

```bash
python _sign_plugin.py sign my_plugin.py --key <PRIVATE_KEY>
```

生成 `my_plugin.py.sig`：

```json
{
  "algorithm": "ed25519",
  "public_key": "<公钥 hex>",
  "signature": "<签名 hex>",
  "signed_files": ["my_plugin.py"]
}
```

把 `my_plugin.py` 与 `my_plugin.py.sig` 一起发布。

### 9.4 签名包插件

在 `manifest.json` 的 `signature` 字段写入同样的结构（algorithm / public_key / signature / signed_files），`signed_files` 建议列出所有被签名文件（入口文件必须包含）。

### 9.5 用户侧信任

用户把公钥加入 `config.json`：

```json
{
  "plugin_trusted_keys": ["<你的 PUBLIC_KEY>"]
}
```

此后你的插件验签通过 → `trusted` → 自动享受放宽的审计与导入限制。

> 默认开启签名校验（`plugin_signature_verify: true`）。未签名的插件仍可加载（`unsigned` 状态），只是按严格审计执行。

## 第 11 章 调试与排错

### 11.1 查看插件状态

前端「插件控制面板」展示每个插件：

- `enabled`：是否启用
- `error`：加载失败原因（无则正常）
- `tool_count` / `hook_count` / `hook_names`：注册的工具数与钩子列表
- `signature_status` / `trusted`：签名状态（trusted / untrusted / unsigned / invalid）与是否受信任
- `isolation`：实际运行模式（process / inprocess）
- `audit_issues`：安全审计结果（critical / warning / info 计数与明细）

### 11.2 日志

- 插件日志：`<app_dir>/plugin.log`（所有插件共用一个文件，每行带插件名）。
- 插件系统日志：通过 Python logging（logger 名 `plugin_system`）输出到控制台。
- 钩子触发记录：调试面板 → 插件钩子触发记录（record_hook），可查看 before/after 数据变形。

### 11.3 热重载

开发插件时不需要反复重启 Agent：

- 前端「插件控制面板」→「重新加载插件」（`reload_plugins`）→ 全量重扫。
- 或 `PluginManager.unload_plugin(name)` 卸载单个插件后再次加载。

> 注意：每次重新加载会清理 `sys.modules` 中的旧插件模块，防止旧模块副作用累积（比如启动线程重复执行）。

### 11.4 常见加载失败原因速查

| 现象 | 原因 | 解决 |
|---|---|---|
| `error: Security audit blocked (N critical issue(s))` | 源码含 CRITICAL 危险调用，且审计为 block | 移除危险调用；或签名后加入信任公钥；或（不推荐）降审计级别 |
| `error: Import blocked: ...` | import 了被限制模块（strict 白名单外） | 改用白名单内模块；或走签名信任通道 |
| `error: Missing required permissions: ...` | manifest 权限声明不足 | 在 manifest.permissions 补充 |
| `error: 插件签名校验失败：...` | 签名 INVALID（文件被改/签名损坏） | 重新签名；确认发布物完整 |
| `error: 插件宿主子进程启动失败...` | 进程隔离宿主起不来 | 检查 Python 环境；临时切换 inprocess（不推荐）调试 |
| 插件列表里没有它 | 没有 TOOLS/钩子/execute，被判定非插件 | 补全插件接口 |
| 工具没生效 | 工具名冲突被跳过 | 改名，确保全局唯一 |

## 第 12 章 进阶主题（重度开发者）

### 12.1 架构：进程隔离与 RPC

```
主进程（PluginManager）
  │  仅维护元数据（PluginInfo：tools/hook_names/signature/…）
  │  JSON 行协议（stdin/stdout，每行一个 JSON）
  │  op ∈ {load, call_tool, fire_hook, set_context, shutdown}
  ▼
插件宿主子进程（python -m plugin_system.plugin_host）
  ├─ 真正 importlib 加载插件模块（sys.modules 前缀 vibe_plugin_）
  ├─ 子进程内继续施加导入限制（纵深防御）
  └─ 空闲 600s 自动退出（HOST_IDLE_TIMEOUT），避免僵尸宿主
```

- RPC 超时：`call_tool` 120 秒；`fire_hook` 5 秒（与钩子超时一致）。
- 响应中的返回值统一经 `_safe_json` 处理：可 JSON 序列化的保持原样，否则转字符串。
- 子进程入口强制 UTF-8 stdout/stderr（Windows 下防止 GBK 中文乱码）。
- 宿主崩溃后，`execute()` 会返回 `Error: plugin host process is not running`；主进程可 kill 重启。

### 12.2 模块加载细节

- 插件模块名固定为 `vibe_plugin_<插件名>`（`importlib.util.spec_from_file_location` 创建）。
- 重复 `discover_and_load` 前会清理 `sys.modules` 中以 `vibe_plugin_` 开头的模块，避免副作用累积。
- 目录去重：按 `realpath` 去重，同一物理文件即使被多个 plugin_dirs 扫到也只加载一次（杜绝重复工具）。

### 12.3 钩子调度语义

- `_broadcast`（非可变钩子）：fire-and-forget，逐个调用，异常吞掉。
- `_broadcast_mutating`（可变钩子）：**第一个非 None 返回值胜出**，其余监听者不再有机会修改。
- 每个钩子回调跑在独立 daemon 线程里（`_call_with_timeout`），5 秒硬超时；超时线程标记为 zombie，`shutdown()` 时统一 join（最多等 2 秒）。
- 进程隔离下钩子通过 RPC 触发：主进程剥离 `PluginContext` 参数（不可 JSON 序列化），子进程 `_sync_context` 补回自己的 context（`storage` 在子进程内持久）。

### 12.4 插件间通信

插件之间**没有**直接通信通道（隔离设计）。跨插件协作的推荐方式：

- 通过文件系统（`context.app_dir` 下的共享目录）。
- 通过 `context.storage` —— 注意：process 模式下 storage 在各自子进程内，不共享。
- 通过 Agent 本身：A 插件把结果写入工具返回，Agent 再调用 B 插件的工具。

### 12.5 安全审计的 AST 检测能力

`PluginSecurity._walk` 覆盖的检测点：

- `ast.Import` / `ast.ImportFrom`：危险模块导入（含父模块前缀匹配）。
- `ast.Call`：危险调用（os.system / subprocess.run / eval / exec 等）。
- **动态绕过检测**（P0-3）：`getattr(os, "system")`、`obj.__getattribute__("popen")`、`os.__dict__["system"]`、`globals()["os"].system`、`vars()["subprocess"].run` —— 危险函数名集合与反射入口点集合见 `DANGEROUS_FUNC_NAMES` / `REFLECTION_ENTRYPOINTS`。
- `ast.Attribute`：`sys.modules` / `sys.settrace` 等系统操纵访问。
- `ast.Subscript`：`__dict__` 下标访问危险名。

**规避静态审计不等于安全**：审计只是第一道门。动态加载（`importlib`）、反射、`ctypes` 在 `block` 级都会被拒；即使绕过，进程隔离 + 网络策略 + 审批仍是兜底。

### 12.6 资源限制（实验性）

`plugin_security_resource_limit: true` 启用 `ResourceLimiter`（加载期）：内存上限 512MB（Unix `RLIMIT_AS`）、CPU 时间 30 秒（`signal.alarm`）。**警告**：这些是进程级限制，若插件在主进程内加载（inprocess），可能影响整个 Agent 进程。默认关闭。

### 12.7 调试技巧

- 进程隔离模式下插件 `print` 不可见：用 `context.logger` 代替。
- 快速单测插件逻辑：把插件模块用 `importlib` 手动加载（模拟 `vibe_plugin_` 前缀 + `_loading_plugin.active`），传入一个假的 context：

mod = importlib.util.module_from_spec(spec)

class FakeCtx:
    project_root = "."
    app_dir = "."
    config = {}
    storage = {}
    current_step = 0
    total_usage = {}
    logger = print

print(mod.execute("say_hello", {"name": "测试"}, FakeCtx()))
```

## 附录 A 常见错误与解决方案

**Q1：插件显示「Security audit blocked」？**
源码里有 CRITICAL 危险调用。检查是否用了 `subprocess` / `eval` / `ctypes` 等。修复方式：移除危险调用（推荐）→ 签名 + 信任（次选）→ 降低 `plugin_security_audit`（不推荐）。

**Q2：`import requests` 失败？**
默认 `strict` 白名单不含 requests。方案：改用 `urllib`？也不在白名单。**正确做法**：需要网络的插件 → 包插件 + 声明 `"permissions": ["network"]` + 签名 + 加入信任公钥（trusted 后导入限制自动为 off）。

**Q3：插件工具调用时 Agent 说「未知工具」？**
工具没注册成功。看插件控制面板：error 字段、tool_count 是否为 0。也检查工具名是否与其他插件冲突（冲突的会被跳过）。

**Q4：钩子没触发？**
- 检查函数名拼写（必须是 HOOK_NAMES 中的精确名称）。
- 检查参数个数与签名一致（最后一个参数必须是 context）。
- 看调试面板的钩子触发记录。

**Q5：修改插件后不生效？**
插件在加载时被 import 一次。改完必须「重新加载插件」（或重启 Agent）。

**Q6：进程隔离模式下 storage 不共享？**
process 模式下每个插件一个子进程，storage 在子进程内持久（跨调用、跨钩子同一插件内是共享的），但**不跨插件共享**。

**Q7：插件崩了会不会影响 Agent？**
不会。process 隔离下插件崩溃只影响宿主子进程；主进程检测到宿主不存活会返回错误信息，可重启宿主。
